# Millwright-Inspector

## The motivation

- Sentences about how ai had influenced the fields and how software engineering became one of the mostly effected field.
- How we had been performing software development, what was our workflow as a frontend or backend developer.
- Development was completely isolated task for people other than developers.
- Review has been one of the tasks that we had been performing. but review was only done in coding/implementation. Reviewing tasks, requirements, testing plans are not common.
- Todays software development is ai driven but there need to be some specialist, a logical thinker to be in the loop.
- In this methodology, each step in the workflow generates artifacts which can be reviewed by you and those artifacts will also be used as the context artifacts in the forthcoming steps.
- Give an example: the generated requirements.md file from the design steap will be used as context in the implementation step agents.
- All steps in the workflow gets artifacts as input to be used as agent context and generates artifacts which are reviewed by the inspectors which are to be used by other steps. The artifacts are called "Context Artifacts" and This mechanism is called "Context Artifact Relay". The "relay" fits the inspector review and send approve signal analogy. This signal triggers the next step in the workflow, so the workflow is basically connected relays.
- Roles are Millwright and Inspector. The Millwright is responsible from generating the artifacts, summoning agents and put the context-artifacts into their contexts, progression of workflow when the inspector approves, so basically it is responsible from making the machine work. Inspector is responsible from checking the quality of the generated context-artifacts and direct the millwright to get better outputs.
- SO the main system is a workflow which is a combined context artifact relays. Millwright generates and uses context-artifacts and inspector inspects the quality of these artifacts and send signals to make the next relay work.
- Becasue that workflow consist of many context artifact relays, inspectors can easily handle multiple workflows at the same time. They dont need to focus with 100% attention to a workflow, they can inspect a context artifact relay and send the signal, while waiting for the next relay to be run they can switch to another workflow and inspect another relay there. Example: Inspector inspects blueprint step which generates requirements.md, after inspecting and approving it, the next relayi implementation will be run, while this is running, inspector can move on to another workflow and inspect the manual-test-plan.md of that workflow. They dont need to inspect the whole workflow.
- Collaboration between inspectors can also be possible: One inspector can open the generated requirements.md file to a review from other inspectors, while that inspector can also inspect the implementation of another inspector etc.
- TODO tasks which are managed with JIRA,Linear are also considered as context-artifacts and can be saved in static files late to be used in contexts for generating reqirements, design files, diagrams etc. Saving the tasks as context-artifacts is also beneficial
since these artifacts can directly be accessed by agents, can be filtered, used as source for statistical data derivation, watching the progression of the overall feature, filtering by semantics etc. So non-technical workers can also make use of them.
- Since each workflow keeps their own progression, these can also be used by PM's, customers etc for monitoring the overall progression, calculating the team pace etc.
- Codebase becaomes another context-artifact which can be read and analyzed by anyone including customers, PMs, analysts etc. So once the resource (codebase) which cannot be read except by developers can now be read via agents and used as a resource for deriving other data from it.
- Context artifact repositories are the folder in the codebase which the generated context-artifacts are stored. There are 3 main repository directories except the codebase itself. "Journal" keeps the resources which are to be used for planning and creating the tasks from. These can be any resource files like pdf's, .doc files, .md files, images, database connections, external resources, api calls, mcp etc. "Quest" keeps the distilled summary of the journal and the derived tasks from the journal. "Workflow Stream" keeps the blueprints (requirements, pre -implementation UML diagrams) and the implementation related resources such as post-implementation UML Diagrams, manual testing plans and results, review files, inspector notes etc.
- Anyone can use these context-artifacts as the resources and create their custom apps like: tracking the feature progression, send notifications when a feature workflow is completed, list workflows which are blocked more than 1 hour, workflows which are ready for manual testing etc.
